A

一次推荐请求的全流程

点「AI 顾问」发一句话 → 下面这 9 步。编号 4–8 全在后端，前端只看得到 SSE 事件。

1

前端 发起请求

组件 AIAdvisor → POST /api/ai/recommend/stream，带 userRequest、可选心境、以及从服务端拉回来的对话历史。

不传书库
请求体只有 KB 级；书库与画像一律后端从 SQLite 取，客户端传了也不算数
卸载即中止
切页会硬重挂载，useEffect(() => () => abort()) 不加就会遗留 SSE 占住浏览器 6 条连接之一
2

后端路由 鉴权 → 校验 → 装上下文

requireAuth（JWT）→ Zod 校验请求体 → createAgentContext(userId)。

装进来什么
书库（books）、画像（user_profiles + 逐字段来源 profile_field_meta）、采纳反馈摘要（recommendation_feedback）
请求级作用域
工具结果缓存 / 联网调用计数挂在 ctx 上，随请求生灭（早先是模块级全局 → 会跨用户串）
3

Agent 组装提示词（每次请求 11.5k token 的固定开销）

详见 B 段。要点：静态部分占 88%，真正属于"你的数据"的只有 12%。

4

Agent Phase 1：静默工具循环（≤ 4 轮，非流式）

模型决定调哪些工具 → 并行执行 → 结果按原顺序塞回 messages → 再问一轮。全程不推送给用户，只推 reasoning 与 tool_call 标签。

为什么是 4 轮
101 本以上概览不注入书名，模型必须先查工具才拿得到真实 bookId；实测 413 本库上"从书架挑三本"恰好用满 3 轮，第 3 轮既是查询轮又是收敛轮
写工具的副作用
任何写操作都会 toolCache.clear()，让同轮后续工具读到新值
5

闸门 两道结构性强制（不是劝导）

提示词中间的话会被稀释（370+ 行系统提示里，"落盘才算记住"写在 第 35 行）。所以关键规则改成结构强制：

书库硬闸门
声称给了 libraryMatches 却一次书目工具都没调 → 追加 1 轮纠正（≤100 本不启用，概览里就是全量书名）
本次请求：已启用
画像落盘闸门
用户消息命中"我的水平 / 我的目标是 / 我每天能读 40 分钟"这类自述，而模型一次 update_user_profile 都没调 → 追加 1 轮
本次请求：未启用（这句话里没有自述）
6

Agent Phase 2：流式出最终 JSON

基于工具收集到的内容流式生成，SSE 逐块推 chunk。若 Phase 1 最后一轮已经是合法 JSON，则跳过 Phase 2 直接输出（省一次调用）。

7

校验 服务端清洗模型输出

validateAdvisorJson 逐条核对 libraryMatches：ID 对得上保留 → 对不上用书名反查修复 → 修不掉才丢弃；externalMatches 用同一套书名归一化查重（提示词禁止推库里的书，模型仍会犯）。

为什么必须在服务端做
前端渲染是按 bookId 找书、找不到整条不画，一个幻觉 ID 会让人以为"模型只推了 2 本"
回传
matchValidation { kept, repaired, dropped, droppedTitles, externalDuplicates }
8

落库 记录"这次展示了哪些" + 回传

写 recommendation_feedback 的 action='shown' 行（采纳率的分母），并用服务端生成的 requestId 串起来 → done 事件回传完整结果。

9

前端 渲染 + 两条回写

渲染
卡片用 done 里那份（已清洗），不是 chunk 原文
回写 ①
点「想读 / 跳过」→ POST /api/ai/recommend-feedback，带服务端给的 requestId，下次推荐会在【采纳反馈】段读到
回写 ②
AI 改过书状态时收 book_update → patch 回 useBookLibrary，否则客户端下一次整库全量保存会把刚写的状态冲掉
回写 ③
回答渲染完后，再发一次回合后画像抽取（两道零成本闸门先挡）→ 真有写入就弹「AI 记住了…（撤销）」提示条

C

它手里有什么：12 个工具

8 读 + 2 写 + 2 联网（联网需 EXA_API_KEY）。"书目类"才是这次算不算真查过书库的判据——画像类不算，否则一次 get_user_profile 就能蒙过书库硬闸门。

工具类型能拿到什么谁在用
search_library读书目按关键词/分类/标签/状态/难度搜书，返回 15 条简报（关键词已覆盖分类与子分类）推荐、管家
get_book_details读书目单本详情：AI 解读、豆瓣摘要与标签、阅读进度、笔记推荐、问答
get_category_stats读书目某分类全部书籍 + 统计（这是 >300 本档取书名的主力）推荐
get_reading_history读书目最近读完的列表（完成日期、评分、豆瓣分）推荐
get_reading_taste_profile读书目品味全量版：知识结构、轨迹、评分倾向、阅读人格（无行为数据时明确拒绝推断）推荐
get_reading_gaps读书目知识缺口：深度/广度/应用/进度/积压（未读多但无行为时判为 catalog_not_started，不再劝退推荐）推荐
get_reading_notes读书目用户在某本书上写的笔记与思考问答、管家
get_user_profile读画像按来源分组返回：userStated / aiRecorded / unset推荐、管家
update_book_status写改阅读状态/进度/自评星级 → 直接落 SQLite + book_update 通知前端推荐、问答、管家
update_user_profile写写画像（带来源保护，见 E 段）推荐、管家
web_search联网搜互联网（书评、书单、作者、学术），单次对话最多 5 次推荐
web_fetch联网取指定 URL 正文推荐
D

写操作的两条闭环

① 改书：update_book_status

  1. 模型调用 → 只写 books 里 Agent 真正改过的列
  2. 自评星级写进 user_data.userRating（JSON），不碰 books.rating（那里躺着导入期的豆瓣分）
  3. ctx.toolCache.clear()，同轮后续工具立刻读到新值
  4. 推 book_update 给前端 → patch 内存副本

漏接 book_update 不会丢 AI 的写入，但客户端下一次整库全量保存会把它冲掉——所以新增流式端点一律走 sseHandlers()，它不做取舍。

② 记人：update_user_profile（对话中）

  1. 必填 evidence（用户原话）与 userStated（是不是用户本轮亲口说的）
  2. 写入函数按字段判来源 → 用户来源的字段直接拒绝
  3. 被拒的进 refused 回给模型 → 它必须如实说明"这条是你自己定的"
  4. 成功的写 profile_field_meta（source / via / evidence）+ profile_write_log

实测：加尾部指令与闸门之前，27 次真实请求里模型调用此工具 0 次；之后两轮探针都在第 1 轮就写进去了。

③ 记人：回合后异步抽取 /api/ai/profile/extract

  1. 回答已经渲染完之后才发（用户看不到这次等待）
  2. 两道零成本闸门：顾问本轮已落盘 → 跳过；消息未命中自述正则 → 跳过（"你好呀"实测 0.0s、零调用）
  3. 命中才花一次廉价调用（无工具、无概览，实测 7.3–7.7s），逐字段带原话依据
  4. 一律记为 AI 来源：它没被用户要求过，所以覆盖不了用户定的字段
  5. 当场弹「AI 记住了…（撤销）」→ POST /api/ai/profile/undo 精确还原

为什么要这条路：让模型"顺便记住"不可靠（0/27）。设置页还有完整的「画像改动历史」，值的前后对比与逐条撤销都在那儿。

画像字段的四档来源（注入给模型时就是这么标的）

用户自己定的 不可覆盖

设置页填的（via=form）或用户在对话里亲口说的（via=conversation + 原话）。注入语："权威，不要覆盖、不要否定；只有用户明确要求改时才动"。

AI 记录/推断的 可修正

只能填空白字段或改自己写过的，必带依据。注入语："是推测，可能不准；与用户当前说法冲突时以用户为准"。

数据库默认值

有值却无来源记录（如注册时写的 beginner）。注入语："用户从未确认过，不要当作用户的要求"。这一档就是过去"默认值冒充用户自述"的收口。

尚未设置

注入语："可以自然地问，问到后用 update_user_profile 落盘"。

F

21 个 AI 端点里，界面上真正在用的只有 12 个。其中 5 个"数据类"（反馈 2 + 会话 3）本轮才接上；剩下 9 个生成类端点完全没有调用方——它们不出现在任何按钮背后，所以你永远看不到它们跑。

G

能力边界：它现在不能做什么

⚠️ 长期记忆：结构化那半已通，自由记忆还没做

已经有：会话记忆（conversations）+ 结构化画像（4 字段 + 来源 + 保护 + 可撤销）+ 回合后异步抽取。
还没有：没有槽位的事实与约定（"我在准备考试""我不看成功学"）——设计已写在路线图 §16，等真实使用数据积累后再做；读取必须靠检索而非全量注入，否则会稀释指令。

❌ 不记"读过哪些行为"

没有阅读行为流水表。热力图只能按开始/完成两个离散事件计数，做不到"每天读了多久"；"进度 0%"到底是没读还是没记录，系统分不出。

❌ 采纳率还没有真实数字

分母机制（shown）本轮才建好，要等真实点击才有 wantRate。而且这些信号目前只影响排序偏好，不参与任何自动评估。

❌ 评估还是一次性采样

9 条 query、每条跑一轮，噪声大到分不清"改动有效"和"模型随机"。没有人工三维评分（相关性/多样性/难度适配）。

❌ AI 的主观判断没有回写通道

模型在推荐里说"《X》其实不适合你现在读"，这句话不会落到任何地方影响下次结果。评分类主观数据（分类/难度/解读）只在导入期生成一次。

❌ 没有向量检索 / 协同过滤

路线图里明确列为非目标（个人书库信号量不够喂）。检索全靠 SQL LIKE + 分类过滤。

H

自查入口（随时可跑，零 token）

cd backend && npm run build node inspect-context.js # 本次请求往模型里塞了什么（就是本页 B 段的数据来源） node inspect-context.js --query="我每天能读 40 分钟" # 看闸门是否被这条 query 打开 node check-validation.js # 推荐输出清洗：幻觉 bookId 修复/丢弃、站外去重（6 项） node check-profile-provenance.js # 画像来源、覆盖保护、改动日志与撤销（27 项） node eval-advisor.js --run --tag=after --model=step-3.7-flash # 真实模型评估（计费） node eval-advisor.js --compare=baseline,after # 前后对比（零成本） node eval-advisor.js --extract="我每天能读 40 分钟" --undo # 验证回合后抽取与撤销（一次廉价调用）

前三个不花钱、不联网、只读你的库快照（VACUUM INTO 到 backend/.eval-run/，已 gitignore）；后两个直连真实模型。
